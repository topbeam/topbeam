What should you do next?

Topbeam reads your Claude Code transcript and git itself, deterministically — no LLM call, everything stays on your machine. The one outward question is optional and can be switched off: “is this commit green in CI?” (--no-ci). The model's “done, it works” sentence cannot enter the summary; only records can.

Topbeam does not tell you the story of your project; it tells you what is true right now, and the one move that gets you further.

How it works

Three commands and one habit. Four more when you need them.

  1. 01

    npx topbeam init

    Connects the project. It creates the working folder (named .ocean/ — left from the product's old name, kept so existing installs are not put through a migration) and adds a .ocean/ line to your .gitignore, because that folder holds the text of the commands you ran. It also offers to append a short Topbeam section to your CLAUDE.md: it prints the exact text first, then asks. Without a terminal it does not ask and does not write. --claude-md says yes up front, --no-claude-md says leave it alone.

  2. 02

    Work as usual

    Carry on with Claude Code the way you already do. Topbeam asks for nothing in between, does not interrupt you, and does not make you keep a second record somewhere.

  3. 03

    npx topbeam sync

    Reads the transcript records and the git facts, then produces evidence-levelled claims, the log history and the card. Writes .ocean/pano.html.

  4. 04

    npx topbeam open

    Prints the path to the board. It does not open your browser — you do.

One command is only for you: npx topbeam verify <id> — it shows a claim's evidence and asks for your approval. Human approval is the only legitimate way a claim moves up, and it is never taken back: work you do later in the same area does not empty a promise you already signed. TERMINAL ONLY: if the answer arrives from a pipe or a script, nothing is recorded. That stops approval from happening by accident — but it is a speed bump, not a wall: script(1) opens a fake terminal, and someone who deliberately wants to automate approval gets past it. When every delivery promise has been approved, one notification fires and a seal is written.

One command looks outward: npx topbeam makbuz — it writes the one-page delivery receipt you can paste to a client, a teammate or an employer (.ocean/makbuz.md; --html for a single-file HTML). Inside it: the delivery promises with their evidence levels, an evidence summary, what fell outside the scope, and the verification commands the other side can run on their own machine (commit SHAs, the test command, the approval ledger). An unapproved item never appears approved. For anything it did not measure, the receipt says “I don't know” — not “it isn't there”.

The npx commands above work today — the package is published on npm (topbeam@0.1.2). Package name and command name are the same: topbeam. If you install it globally (npm i -g topbeam) they shorten to topbeam sync — that is the name the board prints in the published version.

Some of what you deliver never touches the machine: someone used it, someone said it was worth it. npx topbeam gozlem "<text>" records that in your own words, signed with your operating-system username, append-only. It is not evidence — its level stays “not verified”, and the board keeps it apart from the measurements under a human-statement badge. You can still approve it later with verify; approving was always a person's job. (gozlem and makbuz keep their Turkish names — they are the words already in your fingers.)

Leaving is a command too. npx topbeam uninstall takes back the traces the tool left in your files: the CLAUDE.md section and the .gitignore line. It deliberately leaves .ocean/ where it is — the signed approval ledger inside cannot be produced again. --purge removes that folder as well, and prints what you are losing first.

One warning the tool gives you rather than hides: Claude Code deletes its transcripts after cleanupPeriodDays, 30 days by default. Once they are gone, the file and test evidence cannot be produced again. From day 25 onward sync says so out loud. What survives is the approval ledger in .ocean/passport.jsonl, because you signed it.

The product's constitution

“Changed” and “works” are not the same thing.

Topbeam never puts the two in the same box. Every claim carries a level.

  • Evidenced

    There is a change visible in the git record, or a test result read out of the output. If no number could be read, the claim is not raised.

  • Looks applied

    There is an edit record, but no counterpart in git. Topbeam does not say “it happened” here; it says what it does not know.

  • Not verified

    No evidence. The model's statement sits in the log under a “statement” badge — it does not count as evidence.

These are the labels the tool actually prints: File evidence — confirmed against the git diff · Test evidence — confirmed by test output · Human approval — a person checked it in their terminal · Not verified — looks applied, nobody has confirmed it.

One thing stays Turkish on purpose: the keys written to disk (dosya-kaniti, test-kaniti, insan-onayi, dogrulanmadi) and the data directory .ocean/. They are the storage schema — renaming them would orphan the approvals already signed in passport.jsonl on existing installs. You will see them if you open state.json; you will not see them in the interface.

  • A claim with no evidence is not shown.
  • “It works” is never said automatically — only with test evidence, or your approval.
  • Numbers are not invented; if one could not be read, the claim stays not verified.
  • No percentage progress, no encouragement, no red alarms.
  • Human approvals are never taken back — the ledger is append-only, and new work does not lower the bar.
  • Every piece of text that goes to disk passes a secret-masking filter, which does not claim to know every pattern.
  • Writes never follow a symlink (O_NOFOLLOW) and never leave the project root; a refused write exits with code 2, so a script can tell it apart from an ordinary error.
  • A mislabelled honesty badge is worse than no badge at all — so where the tool cannot measure, it says so.

The core is free. The core is open.

What is true today

There is no Pro yet. No payment page, no licence check in the code, and two of the items above are simply unwritten today: passport history that travels between projects does not exist (all state lives in that project's own .ocean/ folder, with no link between projects), and no limit on the number of projects is enforced anywhere. The table above is a plan, not a product — it is here so you know before you install, not so you find out afterwards.

Which is why I am not offering “Pro free for the first 10 users”: you cannot give away something that does not exist. Today everyone has everything, because nothing is locked. If the paid tier ever gets written, it will say so here first.
